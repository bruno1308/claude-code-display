# Claude Display — Glasses → Claude Code Bridge

**Date:** 2026-05-17
**Status:** Draft for review
**Owner:** brunofernandeslopes@gmail.com

## 1. Goal

Send voice commands from Meta Display glasses to an interactive Claude Code session running on a personal Windows PC, and see the assistant's reply on the glasses. Same conceptual product as [Happy](https://github.com/slopus/happy), but the client is a Meta Wearables web app instead of a phone.

**v1 success looks like:** wearing the glasses anywhere with internet, I press talk, say "what's the status of the auth refactor", and within a few seconds Claude Code's response appears on the display — generated by the same `claude` process I left running in a terminal on my PC, on my Claude subscription.

## 2. Non-goals (v1)

- TTS readback of responses (text-out only).
- Streaming tool-call visualization (we ship the final assistant text; tool calls happen but aren't rendered on glasses).
- Mobile/phone client.
- Multi-user / team support. Single user, single PC.
- Web dashboard / history viewer.

## 3. Constraints

- **Subscription-billed Claude only.** Must use the existing interactive `claude` process (not `claude -p` or the Agent SDK), because programmatic modes require separate API billing.
- **Primary OS: Windows.** Mac/Linux can come later; design must not assume POSIX-only primitives.
- **End-to-end encrypted.** Relay should not be able to read prompts or responses.

## 4. Architecture

```
                          ┌──────────────────────────────────┐
                          │  Vercel project (one deploy)     │
                          │                                  │
┌──────────────┐  HTTPS   │  GET /        → static webapp    │   WSS/E2E    ┌────────────────┐
│ Glasses      │ ────────▶│  WSS /ws      → relay function   │◀────────────▶│ mw-claude      │
│ webapp       │◀────────▶│  POST /stt    → Whisper proxy    │  ciphertext  │ wrapper (PC)   │
│ (browser)    │  WSS/E2E │                                  │              │                │
└──────┬───────┘ciphertext└──────────────────────────────────┘              │ ┌────────────┐ │
       │ mic                                                                │ │ child PTY  │ │
       ▼                                                                    │ │  claude    │ │
   Web Speech API ── fallback ──▶ Whisper API                               │ └────────────┘ │
                                                                            └────────────────┘
```

Three logical components: **glasses webapp**, **relay**, **PC daemon (`mw-claude`)**. The webapp and relay live in a single Vercel project (one host, one domain). The relay is a dumb encrypted message bus; all logic lives at the endpoints.

## 5. Components

### 5.1 Glasses webapp

Scaffolded via the `meta-wearables-webapp:create-webapp` plugin skill. Built with React + Vite (whatever the scaffold gives us).

**Screens:**
- **Pair** — first run only. Shows a QR scanner. User scans the QR shown by `mw-claude` on their PC. Stores keypair + relay session in IndexedDB.
- **Session picker** — list of currently-running `mw-claude` sessions (label = working directory basename + last activity time). Tap to select.
- **Prompt** — big hold-to-talk button. While held, captures mic audio and shows interim transcript. On release, sends final transcript to the relay. Below the button: a scrollable view of the last few exchanges (you-said / claude-said), latest at bottom.

**STT path:**
1. Try `window.SpeechRecognition` / `webkitSpeechRecognition` (Web Speech API) — if available in the Display browser, free + on-device, no network needed.
2. Fallback: record `MediaRecorder` to webm, POST to a small `/stt` endpoint on the relay that forwards to OpenAI Whisper. (User's OpenAI key, stored in PC daemon config, never touches the relay in cleartext — see §7.)

We'll detect availability at runtime and prefer Web Speech when present. Both paths land in the same place: a final text string ready to send.

### 5.2 Relay (Vercel, same project as the webapp)

Lives in the same Vercel project as the webapp — one deploy, one domain. Next.js App Router; the webapp is the static/React surface, the relay is a route handler under `/ws`. Two responsibilities:

1. **Routing.** Each pairing has a `channel_id`. Glasses and `mw-claude` both connect via WebSocket (`/ws?channel=<id>&role=client|daemon`). Relay forwards any frame from one side to the other.
2. **Whisper proxy** (optional, see §7). `POST /stt` accepts encrypted audio and forwards to the daemon for transcription, so the relay never sees plaintext audio.

**Transport choice — WS vs SSE on Vercel.** Vercel Fluid Compute supports both. We default to **WebSocket** because we need bidirectional traffic and the protocol is simpler than SSE+POST for our case. Fluid functions have a max execution window (300s default, configurable up to plan limits) — clients reconnect on close with the same `channel_id` and resume. We'll design both endpoints to be reconnect-tolerant from day one (no in-memory session state that can't be reconstructed).

**Pricing note.** Active CPU pricing means an idle WS still costs while it's pinned to a function instance. For a single user with at most a handful of channels this is negligible; we revisit only if scaling.

**State.** No database. Channels are ephemeral routes — when both ends are connected to the same Vercel instance, frames forward in memory. When they land on different instances (Fluid scale-out), we need a cross-instance fan-out. v1 picks the simplest of these during planning: a tiny Upstash Redis pub/sub channel keyed by `channel_id`, or Vercel Queues. Either way, no durable storage of message content.

### 5.3 PC daemon (`mw-claude`)

A Node CLI installed globally: `npm i -g mw-claude`. The user runs `mw-claude` instead of `claude` in their terminal.

**Responsibilities:**
- Spawn `claude` as a child attached to a **ConPTY** via `node-pty` (Windows). Mirror PTY ↔ user's terminal in both directions so the experience is indistinguishable from running `claude` directly.
- Maintain a WebSocket to the relay using the channel from `~/.mw-claude/config.json` (created at pairing).
- Announce itself as a "session" with label = `path.basename(cwd)` + PID.
- On `prompt` message from relay: decrypt, write `text + "\r"` into the child PTY's stdin.
- On PTY output: buffer, strip ANSI, segment into assistant-reply chunks (see §8), encrypt, send to relay.
- Run a pairing subcommand: `mw-claude pair` → generates ECDH keypair, displays a QR encoding `{channel_id, daemon_pubkey, relay_url}`, waits for glasses to connect and complete handshake.

**One daemon = one session.** Multiple sessions = multiple `mw-claude` terminals. The glasses session picker lists every daemon currently online for the user's channel set. (Channel set = bundle of channel IDs the glasses have paired with. Each pairing adds one.)

## 6. Data flow

**Prompt (glasses → claude):**
1. User holds talk button → STT produces final text.
2. Glasses encrypt text with daemon's public key (libsodium `crypto_box`), wraps in `{type:"prompt", session_id, ciphertext}`.
3. Relay forwards frame to the selected daemon by `session_id` → `channel_id` mapping.
4. Daemon decrypts, writes to child PTY stdin.

**Response (claude → glasses):**
1. Child `claude` emits TUI output; daemon's PTY reader buffers.
2. Reply segmenter (§8) emits "assistant message complete" with cleaned text.
3. Daemon encrypts with glasses' public key, sends `{type:"reply", session_id, ciphertext}` to relay.
4. Relay forwards to glasses. Glasses decrypt, append to transcript view.

## 7. Pairing & encryption

- Keys: X25519 (libsodium `crypto_box`) for asymmetric, XChaCha20-Poly1305 for symmetric session keys. Both endpoints generate keypairs locally; private keys never leave the device.
- Pairing payload (QR): `{ v:1, channel_id, daemon_pub, relay_url, openai_proxy_token }`.
- Glasses POST `{channel_id, glasses_pub, sealed_handshake}` to relay; daemon picks it up over its socket, completes handshake → both sides have each other's pubkeys.
- Relay only sees: channel IDs, ciphertext, frame sizes, timing.

**Whisper proxy token:** at pairing, daemon generates a random per-channel token, embeds it in the QR. Glasses send it as `Authorization` on `/stt` calls. Relay holds a map `token → channel_id` and a per-token rate limit. *Open question for planning: do we proxy through relay at all, or have glasses post audio E2E-encrypted through the WebSocket and let the daemon call OpenAI? Latter is cleaner; chosen during planning.*

## 8. Output parsing (the hard part)

The TUI emits a lot of ANSI: spinners, syntax highlighting, the input box redraw, etc. We need "the assistant's reply, in readable plain text."

**v1 strategy — bounded heuristic:**

1. Strip ANSI escape sequences (`ansi-regex`).
2. Track the "user input prompt" line pattern that Claude Code draws — when we see it appear *after* having seen post-prompt content, that's the boundary; the chunk between two prompts is one turn's response.
3. Within a turn, drop lines that match Claude Code's chrome (header lines like `╭─...─╮`, spinner frames, status messages). Keep code blocks and prose.

This is heuristic and brittle. We accept that and ship a **debug mode** flag in `mw-claude` that dumps raw PTY bytes to a file so we can iterate.

**Possible better path:** Claude Code can emit JSONL via `--output-format stream-json`, but only in `-p` mode — which is exactly what's billing-incompatible. So we're stuck with TUI scraping for v1.

**Refinement path (post-v1):** if Claude Code exposes a hook like `UserPromptSubmit` / `AssistantMessage` that fires during interactive runs, we can register a hook that writes structured events to a local socket the daemon reads. Worth exploring once the heuristic version is working.

## 9. Error handling

- **Daemon disconnect from relay:** auto-reconnect with exp backoff. While disconnected, glasses show that session as "offline."
- **Glasses send prompt to offline session:** relay returns `{type:"error", code:"session_offline"}`, glasses show a banner.
- **PTY child dies (user quits claude):** daemon detects, emits `session_ended`, exits. User must re-launch.
- **STT failure:** glasses show error, keep recording buffer so user can retry without re-speaking.
- **Pairing collision:** if a QR is scanned twice, the second pairing replaces the first (last-write-wins, simple).

## 10. Testing

- **Unit:** ANSI stripper, reply segmenter (golden-file tests against recorded PTY dumps), crypto envelope round-trips.
- **Integration:** spin up relay locally, fake daemon that echoes prompts, fake glasses client that asserts the round-trip + decryption.
- **Manual:** the only realistic test of the full loop is on actual Display hardware. We'll use the `meta-wearables-webapp:test-on-device` skill flow during dev.
- **Windows PTY validation: do this first.** Before building the relay or webapp, write a 50-line spike that confirms `node-pty` on Windows can: (a) spawn `claude` interactively, (b) mirror to the parent terminal cleanly, (c) accept programmatic stdin writes. If this fails or is too rough, we pivot to the tmux/Windows Terminal–based fallback.

## 11. Risks

1. **Windows PTY ergonomics** — biggest unknown. Validation spike first.
2. **TUI output parsing** — heuristic; will need iteration. Debug-dump mode mitigates.
3. **Web Speech API in the Display browser** — unclear if supported. Whisper fallback is the safety net.
4. **WebSocket on Vercel Fluid Compute** — supported, but functions have a max execution window so clients must reconnect periodically. Both endpoints must be reconnect-tolerant. Active CPU pricing applies to idle pinned connections; acceptable for single-user scale, revisit if it grows.
5. **Cross-instance fan-out** — if Fluid scales out and the two ends of a channel land on different instances, in-memory routing fails. v1 mitigation: Upstash Redis pub/sub (or Vercel Queues) keyed by `channel_id`. Decide which during planning.

## 12. Open questions (resolve in implementation plan)

- Whisper proxy: through relay or direct from daemon over WS-tunneled audio?
- Session label: `cwd` basename, or let the user type a label when launching `mw-claude --label "auth-refactor"`?
- Multiple paired PCs: out of scope for v1, or trivially supported via channel-set design?
- Cross-instance fan-out backing: Upstash Redis pub/sub vs Vercel Queues. Pick during planning based on latency + setup overhead.
